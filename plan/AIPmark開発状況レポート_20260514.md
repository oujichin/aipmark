# AIPmark 開発状況レポート

作成日: 2026年5月14日

## 1. 要約

AIPmarkは、プライバシーマーク（Pマーク）取得・更新に必要な作業を、単なる文書作成ではなく「PMSの運用そのもの」として進めるシステムである。企業情報、業務プロセス、個人情報管理台帳、リスク分析、証跡、確認質問、出力文書を一連のデータとして扱い、AIエージェントが調査・整理・質問・文書化を支援する構想になっている。

現時点では、要件定義だけでなく、Next.js / Prisma / SQLite を使ったMVP実装が存在している。企業名・URL・資料を入力して調査セッションを開始し、AIエージェントが企業情報、業務プロセス、個人情報項目、リスク評価、確認質問を構造化データとして蓄積するための基盤は実装済みである。一方で、Pマーク運用全体を本番利用できるレベルにはまだ達しておらず、RBAC、承認ワークフロー、監査・教育・委託先管理・インシデント管理、正式なWord/PDF/Excel出力、マルチテナント運用、証跡ファイル管理などは未完成または限定実装である。

完成時の価値は、「Pマーク担当者が審査書類を手作業で作る」のではなく、「日々のPMS運用を記録していくと、申請書類、台帳、リスク分析、監査対応資料、変更説明が自然に生成される」体験にある。特許申請を検討できる可能性がある新規アイディアとしては、AIによる段階的PMS構築、根拠付き推定と確認ステータス管理、審査様式への差分説明生成、PMS運用ログからの申請パッケージ自動生成などが挙げられる。

## 2. 現在できていること

### 2.1 要件・設計面

以下のドキュメントが整備されている。

- システム計画書
- データモデル
- 機能要件
- MVP実装計画
- 未実装モジュール要件定義
- 要件レビュー、最終承認、設計バージョン資料

これにより、AIPmarkが目指す方向性はかなり明確になっている。特に、以下の設計思想が固まっている。

- 文書生成ツールではなく、PMS運用基盤として設計する
- 申請書類、証跡、変更説明は運用データの副産物として生成する
- 業務プロセス、個人情報、リスク、管理策、証跡、承認履歴をトレーサブルに接続する
- AIは最終判断者ではなく、候補生成・要約・不足確認・構造化を支援する
- 監査責任者と個人情報保護管理者の分離、自己監査禁止、トップマネジメント承認など、Pマーク実務上の職務分掌を前提にする

### 2.2 実装済みのMVP基盤

現在のリポジトリには、Next.js 15 / React 19 / TypeScript / Prisma / SQLite を使ったWebアプリケーションが存在する。主な実装済み要素は以下の通り。

- トップページから企業名、企業URL、関連資料を入力してAI調査セッションを開始できる
- `templates/pmark` 配下に既存のPマーク資料テンプレート群を保持している
- アップロードAPIがあり、Word / Excel / PDF / TXT / CSV 等の資料を受け付ける前提がある
- Prismaスキーマに、企業、会社プロフィール、業務プロセス、個人情報項目、本人種別、保管場所、第三者・委託先、業務プロセス別個人情報、証跡、リスク評価、質問、文書、変更ログ、AIセッション、チャット履歴が定義されている
- AIエージェントのセッション管理、SSEによるリアルタイム更新、AIツール呼び出し結果のDB保存が実装されている
- ダッシュボードで、企業プロフィール、進捗、業務プロセス、個人情報台帳、リスク、未確認項目、AIメッセージを確認できる
- 業務プロセス単位でAIとチャットし、詳細確認を進める画面がある
- 個人情報台帳の各項目について、`confirmed` / `estimated` / `unconfirmed` / `insufficient_evidence` のような確信度を扱える
- AIが出した推定値を人間が確認・修正する導線がある
- フィールド変更ログにより、AIまたは人間による変更履歴を残す設計になっている
- リスク評価では発生可能性と影響度からリスクスコアを算出する基礎実装がある
- `personal_info_registry`、`risk_analysis`、`business_process_list`、一部様式出力の入口が定義されている

### 2.3 AI連携の実装状況

AI連携については、Anthropic SDKを用いたManaged Agent連携の実装が存在する。AIエージェントは以下の段階的な作業を行う前提で設計されている。

1. 企業基本情報の収集
2. 業務プロセスの洗い出し
3. 業務プロセスごとの個人情報取扱いの深掘り
4. リスク評価
5. 台帳・文書出力

AIからの出力は単なる文章ではなく、`report_company_profile`、`report_findings`、`report_detailed_findings`、`report_risk_assessment`、`generate_questions`、`export_registry` といった構造化ツール呼び出しとして受け取り、DBに保存する設計になっている。この点はAIPmarkの中核的な差別化要素である。

## 3. 未完成・課題が残っていること

### 3.1 Pマーク運用全体の業務モジュール

現時点で中心的に動いているのは、企業調査、業務プロセス洗い出し、個人情報台帳、リスク評価、AI確認質問のMVPである。要件で定義されている以下の領域は、まだ本格実装が必要である。

- ガバナンス管理
- PMS文書管理
- 教育計画・教育実施・理解度確認
- 委託先評価・契約管理
- 内部監査計画・監査記録・是正処置
- インシデント管理
- マネジメントレビュー
- 更新申請パッケージ生成
- 変更要求と影響分析
- 法令・規格要求事項管理

### 3.2 権限・承認・職務分掌

要件上は、個人情報保護管理者、監査責任者、監査員、部門責任者、現場入力者、トップマネジメントなどの役割が定義されている。しかしMVPでは、ロール別表示やデモユーザーの前提はあるものの、本番レベルのRBAC、承認ワークフロー、自己監査禁止、監査責任者と個人情報保護管理者の分離チェックは未完成と見るべきである。

Pマーク審査対応システムとしては、この領域は非常に重要である。単に「誰でも編集できる」状態では、証跡性・統制性が弱くなるため、今後の優先課題になる。

### 3.3 文書出力

文書出力の入口やデータモデルは存在するが、正式な申請書、個人情報管理台帳、リスク分析表、PMS文書、監査報告書、教育記録、マネジメントレビュー議事録などを、審査提出に耐える品質でWord / Excel / PDFとして生成する部分はまだ限定的である。

特に未完成と考えられる点は以下である。

- 既存テンプレートへの正確な差し込み
- レイアウト崩れの検証
- 版管理
- 承認済み文書とドラフト文書の区別
- 出力時点の根拠データ固定
- 審査指摘に対する変更説明の自動生成

### 3.4 証跡ファイル管理

証跡モデルは存在し、Web情報やAI判断根拠を記録する構造はある。しかし、証跡ファイルの実アップロード、保管、プレビュー、ハッシュ化、改ざん防止、証跡バンドル化、審査提出単位での固定化は未完成である。

Pマーク実務では「その判断の根拠は何か」を説明できることが重要であり、この領域はAIPmarkの価値を大きく左右する。

### 3.5 本番運用基盤

現在はローカルMVPとしての性格が強い。今後、本番利用するには以下が必要である。

- マルチテナント対応

## 4. 完成したときにもたらす体験

完成したAIPmarkが提供する体験は、従来のPマーク取得支援とはかなり異なる。

従来は、担当者やコンサルタントがヒアリングし、Excel台帳を作り、Word文書を整え、審査直前に不足資料を探し、指摘が出るたびに文書を修正する流れになりがちである。この作業は属人的で、過去の判断根拠が失われやすく、更新審査のたびに再調査が発生する。

AIPmarkでは、企業の業務を入力・確認していくと、システムがPMSの構造に変換していく。AIが公開情報や既存資料から仮説を作り、担当者に必要な質問だけを返す。回答された内容は業務プロセス、個人情報、リスク、証跡、文書項目に自動的に接続される。

その結果、ユーザー体験は次のようになる。

- 最初に企業URLや既存資料を入れると、AIが業務プロセスと個人情報取扱いの仮説を作る
- 担当者はゼロから台帳を作るのではなく、AIが作った候補を確認・修正する
- 未確認、推定、根拠あり、証跡不足が画面上で明確に分かる
- 業務ごとにAIと対話しながら、不足情報を埋めていける
- リスク分析が個人情報台帳と連動し、二重入力が減る
- 教育、監査、委託先評価、インシデント、変更管理が同じPMSデータ上でつながる
- 申請書類や台帳は、運用データから出力される
- 審査指摘に対して「どの業務・どの個人情報・どの根拠・どの変更に関係するか」を説明できる
- 更新審査では、前回からの差分と変更理由を自動的に整理できる

完成形の価値を一言で表すなら、「Pマーク取得・更新を、書類作成プロジェクトから、証跡付きのPMS運用プロセスに変えるシステム」である。

## 5. 特許申請を検討できる新しいアイディア

以下は、特許申請の候補になり得るアイディアである。ただし、実際に特許性があるかは、先行技術調査と弁理士による確認が必要である。ここでは「技術的特徴として切り出せる可能性があるもの」を整理する。

### 5.1 根拠付きAI推定によるPMS台帳自動構築方式

企業URL、公開資料、既存PMS文書、ユーザー回答を入力として、AIが業務プロセス、個人情報項目、本人種別、取得方法、利用目的、保管場所、委託先、保管期間、廃棄方法を推定し、各項目に対して「根拠あり」「推定」「未確認」「証跡不足」の状態を付与する方式。

単なるAI文章生成ではなく、PMS審査に必要な管理項目ごとに確信度と根拠を分解して管理する点が特徴になる。

### 5.2 段階的PMS構築エージェント

AIが一括で最終文書を作るのではなく、企業基本情報、業務プロセス洗い出し、個人情報取扱い深掘り、リスク評価、文書出力という段階を進みながら、各段階で構造化ツールを呼び出してDBに保存し、不足時だけ人間に質問する方式。

特徴は、AIの会話結果をそのまま使うのではなく、PMSの工程状態として管理し、各フェーズの完了条件によって次工程に進める点である。

### 5.3 審査様式テンプレートと運用データの双方向マッピング

様式A/B/C、申請書、個人情報管理台帳、リスク分析表、監査資料などのテンプレート項目を、PMS運用データの項目に対応付ける。テンプレートを作るだけでなく、テンプレート上の不足箇所から、必要な業務情報・証跡・承認・リスク評価を逆引きして質問やタスクを生成する方式。

これにより「書類の空欄」が「運用上の不足」として扱われる。

### 5.4 更新審査向けの差分説明自動生成

前回申請時点のPMSデータと現在のPMSデータを比較し、業務変更、個人情報項目変更、委託先変更、保管場所変更、管理策変更、リスク評価変更を抽出する。その差分について、変更理由、影響範囲、必要な文書改訂、審査で説明すべきポイントを自動生成する方式。

Pマーク更新審査では「前回から何が変わったか」の説明が重要であり、この自動化は実務価値が高い。

### 5.5 PMS運用ログからの申請パッケージ自動生成

教育、監査、是正処置、インシデント、委託先評価、マネジメントレビュー、文書改訂、承認履歴などの運用ログを蓄積し、申請・更新タイミングで必要な証跡を自動選別して、申請パッケージと証跡バンドルを生成する方式。

単なる文書出力ではなく、「どの証跡を提出根拠にするか」を運用ログから自動で選ぶ点が特徴になる。

### 5.6 職務分掌制約を組み込んだAI支援ワークフロー

監査責任者と個人情報保護管理者の分離、監査員の自己監査禁止、トップマネジメント承認必須といったPマーク固有の職務分掌制約を、AIが作成するタスク・承認依頼・監査計画に組み込む方式。

AIが単に候補を出すだけでなく、組織内の役割制約を満たすようにワークフローを生成・修正する点に特徴がある。

## 7. 報告時の結論

現時点のAIPmarkは、完成品ではない。しかし、単なる企画書段階でもない。Pマーク取得・更新に必要な業務プロセス洗い出し、個人情報管理台帳、リスク評価、AI確認質問、証跡管理、出力文書管理の中核データ構造とMVP画面はすでに作られている。

今後の焦点は、MVPで実証できている「AIがPMS構築を段階的に支援する体験」を、審査実務に耐える統制・証跡・文書出力・承認フローに拡張することである。

特許面では、AIによる文書生成そのものではなく、PMS運用データ、根拠付き推定、確認ステータス、職務分掌、審査様式、証跡バンドル、更新差分説明を一体で扱う方式に着目すると、独自性を切り出しやすい。
