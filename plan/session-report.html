3. 作業内容 2: APIレスポンス不整合の修正

3.1 問題

全APIルートのGETハンドラが { items: [...], total, page, limit } 形式でレスポンスを返しているにもかかわらず、ページ側はレスポンスを直接配列として使用していました。これにより items.map is not a function 等のランタイムエラーが発生していました。

3.2 修正パターン

全ページのfetch処理を以下のパターンで統一修正:

// Before
const data = await res.json();
setItems(data);

// After
const data = await res.json();
setItems(Array.isArray(data) ? data : data.items ?? []);

5. 作業内容 4: パフォーマンス最適化

5.1 原因分析

Chrome DevTools Performance Trace による計測で、以下の原因を特定しました:

原因影響該当ページ
クライアントコンポーネントのuseEffect fetchパターンRender Delay 3〜4秒12ページ
監査ページのN+1問題（forループ逐次fetch）planの数に比例して遅延/audit
ダッシュボードの大量DBクエリ（26個）TTFB増大/dashboard
Router Cache未設定再遷移時もフルリロード全ページ
loading.tsx未実装遷移時に白画面全ページ

5.2 施策 A: Router Cache設定

next.config.ts に experimental.staleTimes を追加し、動的ページのRouter Cacheを30秒に設定。再遷移時のキャッシュ効果を有効化しました。

5.3 施策 B: loading.tsx スケルトンUI追加

3つのスケルトンUIファイルを作成し、ページ遷移時の白画面を解消しました。

  • src/app/(app)/loading.tsx - 汎用スケルトン（全ページのフォールバック）
  • src/app/(app)/dashboard/loading.tsx - ダッシュボード専用
  • src/app/(app)/audit/loading.tsx - 監査ページ専用

5.4 施策 C: 監査ページN+1修正

/api/audit/plans のPrisma includeに findings を追加し、ページ側のforループ逐次fetchを完全に削除。1リクエストで全データを取得する方式に変更しました。

  • Before: plans取得(1回) + 各planの詳細取得(N回) = N+1リクエスト
  • After: plans取得(findings含む)(1回) = 1リクエスト

5.5 施策 D: サーバーコンポーネント化（7ページ）

LCPが4秒超の遅いページを「サーバーコンポーネント + クライアントコンポーネント」構成に分割しました。

7. 作業内容 6: 不具合修正（company/profile）

7.1 現象

/company/profile ページに遷移すると、ログイン済みにもかかわらず /login にリダイレクトされる。

7.2 原因調査

  1. サーバーログにデバッグ出力を追加し、getServerSessionの結果を確認
  2. セッションは有効（organizationId: "org-demo"）
  3. prisma.organization.findUnique({ where: { id: "org-demo" } }) が null を返却
  4. DBの Organization テーブルを直接確認 → テーブルが空

7.3 根本原因

開発中のDB操作（prisma db push等）でOrganizationテーブルのデータが消失していた。サーバーコンポーネント化により prisma.organization.findUnique を直接呼ぶようになったため、初めて問題が表面化した。

（以前のクライアントコンポーネント方式では、APIの /api/company/profile が 404 を返していたが、クライアント側で黙殺していたため気付かなかった。）

7.4 対応

npm run db:seed でseedデータを再投入し、問題を解決。
