# 要件定義書レビュー — ラウンド1

## 総合評価
**B** — 全体的に高い完成度。JIS Q 15001の主要条項を網羅し、データモデル・API設計・画面設計の粒度も実装に十分。ただし、データモデルの整合性、マネジメントレビューモジュールの欠落、organizationIdスコーピングの一貫性欠如など、修正必須の指摘が複数ある。

## 重大な指摘事項（必ず修正が必要）

### CRI-01: マネジメントレビュー（WF-09）に対応するモジュール/画面が未定義
- **モジュール**: 横断（M-07付近）
- **指摘内容**: 機能要件.mdではWF-09（マネジメントレビュー準備フロー）が定義され、データモデル.mdでは`ManagementReview`エンティティが記載されているが、要件定義書にはマネジメントレビューの画面・データモデル・APIが一切含まれていない。JIS Q 15001 J.4.6.3（マネジメントレビュー）は年1回以上の実施が必須であり、申請時にもレビュー実施サマリーの提出が求められる。M-09がマネジメントレビューサマリーを含める設計になっている以上、レビュー記録のCRUDが存在しなければ成立しない。
- **修正案**: M-07を「監査・是正・マネジメントレビュー管理」に拡張するか、独立のM-07b相当のセクションを追加する。`ManagementReview`モデル（入力資料JSON、決定事項、改善要求、承認者、議事録添付）、対応画面（`/audit/review` or `/review`）、APIを定義する。

### CRI-02: 新規モデルにorganizationIdリレーション・インデックスが欠落
- **モジュール**: M-03, M-04, M-05, M-06, M-07, M-08, M-09
- **指摘内容**: 既存の`RegisterItem`は`BusinessProcess`→`Organization`経由で組織スコーピングしているが、新規モデル（`RiskAssessment`, `PMSDocument`, `TrainingPlan`, `Vendor`, `AuditPlan`, `IncidentCase`, `ApplicationPackage`）には`organizationId`フィールドがあるものの、`Organization`へのリレーション定義（`@relation`）が記載されていない。また、`Organization`モデル側に逆リレーション配列（`riskAssessments RiskAssessment[]`等）の追記が必要。Prismaでは双方向リレーション定義が必須であり、片方だけの定義はスキーマエラーになる。
- **修正案**: 全新規モデルに `organization Organization @relation(fields: [organizationId], references: [id])` を追加し、`Organization`モデルに逆リレーション配列を列挙する。また、`@@index([organizationId])`を全モデルに設定する。

### CRI-03: EvidenceRecordの拡張で既存リレーションとの互換性が未検討
- **モジュール**: エビデンスアップロード
- **指摘内容**: 既存の`EvidenceRecord`は`registerItemId`のみをOptional外部キーとして持ち、`RegisterItem`への`@relation`が定義されている。要件定義書では`riskItemId`, `vendorId`, `incidentId`, `auditFindingId`, `correctiveActionId`を追加する設計だが、これは1テーブルに6つのOptional外部キーを持つポリモーフィックリレーション設計になる。SQLiteでは外部キー制約が緩いので技術的には動くが、以下の問題がある:
  1. どの紐付け先にも属さないレコードを防ぐバリデーションがAPI側で必要
  2. 新規モデル（`RiskItem`, `Vendor`等）側に逆リレーション（`evidenceRecords EvidenceRecord[]`）を定義する必要があるが記載がない
  3. 将来の紐付け先追加のたびにスキーマ変更が必要
- **修正案**: 短期的にはポリモーフィック設計を維持しつつ、各新規モデルの定義に`evidenceRecords EvidenceRecord[]`を明記する。APIではアップロード時に少なくとも1つの紐付け先IDが必須となるバリデーションを追加する。将来的には中間テーブル（`EvidenceLink { evidenceId, entityType, entityId }`）への移行も検討に記載すべき。

### CRI-04: RiskAssessmentとRegisterItem/BusinessProcessのリレーション定義不備
- **モジュール**: M-03
- **指摘内容**: `RiskItem`に`registerItemId`と`businessProcessId`のOptional外部キーがあるが、`RegisterItem`モデルと`BusinessProcess`モデル側に逆リレーション（`riskItems RiskItem[]`）の追記が必要。既存スキーマの`RegisterItem`には`riskItems`配列が存在しないため、追加が必要。また、`RiskAssessment`自体にはどの台帳グループに対する評価なのかを示す`businessProcessId`や`registerItemId`の集約フィールドがなく、`RiskItem`を経由してしか対象を特定できない設計になっている。ヒートマップや年度比較で評価単位を特定しにくい。
- **修正案**: `RiskAssessment`に`targetScope`（ALL / PROCESS / ITEM）と`targetIds`（JSON）フィールドを追加し、評価対象を明示する。既存モデルへの逆リレーション追加を明記する。

### CRI-05: CorrectiveActionとIncidentCaseのリレーション不整合
- **モジュール**: M-07, M-08
- **指摘内容**: `CorrectiveAction`に`incidentId String?`フィールドがあるが、`IncidentCase`側に逆リレーション（`correctiveActions CorrectiveAction[]`）が定義されていない。また、`@relation`定義も`CorrectiveAction`側に記載がない。M-08のAPI設計では`POST /api/incidents/[id]/corrective`で事故起点の是正処置を起票するが、Prismaリレーションなしではincludeクエリが使えない。
- **修正案**: `CorrectiveAction`に`incident IncidentCase? @relation(fields: [incidentId], references: [id])`を追加し、`IncidentCase`に`correctiveActions CorrectiveAction[]`を追加する。

## 中程度の指摘事項（修正推奨）

### MED-01: 既存UserモデルのロールにAUDITORがあるが監査員割当の整合性が不明確
- **モジュール**: M-07
- **指摘内容**: 既存`User.role`に`AUDITOR`ロールが定義されている。一方、`AuditPlan`では`auditorIds`をJSON配列で保持する設計で、ロールベースの権限制御とJSON内IDの二重管理になる可能性がある。監査員は固定ロールではなく年度・計画ごとに割り当てるべきであり、`AUDITOR`ロールの位置づけを明確にする必要がある。
- **修正案**: `AUDITOR`は「監査責任者」のロールとし、個別計画の監査員は`AuditPlan.auditorIds`（または中間テーブル`AuditPlanAuditor`）で管理する旨を要件に明記する。権限設計表に`AUDITOR`ロールの行を追加する。

### MED-02: JSON型フィールドの多用による検索性・型安全性の問題
- **モジュール**: M-05, M-06, M-07
- **指摘内容**: `TrainingPlan.targetDetails`, `AuditPlan.targetDeptIds`, `AuditPlan.auditorIds`, `VendorEvaluation.scores`, `QuizQuestion.options`, `QuizQuestion.correctAnswer`などがJSON String型で定義されている。SQLiteではJSON関数が限定的であり、これらのフィールドでのフィルタリング・集計が困難。既存の`RegisterItem.dataCategoryCodes`でも同様のパターンが使われているが、新規モデルでは改善の余地がある。
- **修正案**: 特にフィルタリングが必要な`targetDeptIds`, `auditorIds`については中間テーブル（`AuditPlanDepartment`, `AuditPlanAuditor`）を定義する。スコアなど表示専用のフィールドはJSON維持でもよいが、型定義（TypeScript interface）を要件に明記する。

### MED-03: 年度（fiscalYear）の型と取り扱いが未統一
- **モジュール**: M-03, M-05, M-06, M-07, M-09
- **指摘内容**: 複数モデルで`fiscalYear String`が使われているが、フォーマット仕様（"2025"? "2025年度"? "FY2025"?）が未定義。年度をキーにした横断クエリ（全モジュールの年度実績を集約）で表記揺れが発生するリスクがある。
- **修正案**: `fiscalYear`のフォーマットを「西暦4桁（例: "2025"）」と統一し、横断的な型定義（`type FiscalYear = string`等）を共通ユーティリティに配置する。バリデーションルールも統一する。

### MED-04: 本人対応・苦情相談モジュール（DataSubjectRequestCase/ComplaintCase）が未対象
- **モジュール**: 横断
- **指摘内容**: データモデル.mdではEntity 35として`ComplaintCase / DataSubjectRequestCase`が定義されており、システム計画書でも本人対応・苦情相談管理が業務領域として挙げられている。しかし、要件定義書の対象に含まれていない。JIS Q 15001では開示・訂正・利用停止等の本人請求対応とその記録保持が求められる。
- **修正案**: 対象外とする場合はその判断と理由を要件定義書に明記する。MVPスコープ外であれば「将来対応」として言及する。

### MED-05: 変更管理モジュール（ChangeRequest / WF-03）が未対象
- **モジュール**: 横断
- **指摘内容**: 機能要件.mdではWF-03（変更申請フロー）が定義され、データモデル.mdではEntity 33として`ChangeRequest`が記載されている。新業務・新SaaS・新委託先の追加時に台帳・リスクへ連動する仕組みは、年次PDCAサイクルの要。しかし要件定義書に含まれていない。
- **修正案**: M-04（文書管理）の拡張として変更管理を含めるか、独立セクションとして定義する。最低限、変更申請の起票・承認・台帳反映連携のフローを記載する。

### MED-06: API設計でPATCHメソッドが一切使われていない
- **モジュール**: 全モジュール
- **指摘内容**: 全APIでPUTのみが使用されている。既存実装（`/api/register/items/[id]`）もPUTを使用しているため一貫性はあるが、部分更新（ステータス変更のみ等）でもフルボディを送信する必要がある。特にステータス遷移（承認/差戻し等）は専用エンドポイント（`/approve`等）が用意されているので大きな問題ではないが、`PUT`の意味を「部分更新可」と明記すべき。
- **修正案**: API設計のセクションに「PUTは部分更新を許容する（送信されたフィールドのみ更新）」と明記する。

### MED-07: TrainingResultにuserIdがあるがUserへのリレーション定義がない
- **モジュール**: M-05
- **指摘内容**: `TrainingResult.userId`はString型で受講者を参照するが、`User`モデルへの`@relation`が未定義。受講者情報の取得にはJOINが必要であり、Prismaリレーションがないとinclude不可。同様に、`ControlMeasure.responsibleId`, `CorrectiveAction.responsibleId`, `IncidentCase.reportedById`等、多数のフィールドが`User`への暗黙参照だがリレーション未定義。
- **修正案**: Userへの参照が必要な全フィールドについて、`@relation`を定義する。Prismaでは同一モデルへの複数リレーションがある場合、`@relation(name: "xxx")`で区別する必要がある点に注意。

### MED-08: 第三者提供管理（ThirdPartyProvisionCase）が未対象
- **モジュール**: 横断
- **指摘内容**: データモデル.mdではEntity 27として`ThirdPartyProvisionCase`が定義されている。`RegisterItem.thirdPartyProvision`フィールド（NONE/DOMESTIC/OVERSEAS）は存在するが、提供先・根拠・本人同意・停止請求管理の詳細を扱うモジュールが未定義。委託先管理（M-06）と重複する部分もあるが、委託と第三者提供は法的に区別が必要。
- **修正案**: M-06の拡張として第三者提供管理のセクションを追加するか、台帳連携として`RegisterItem`の詳細画面内で管理する設計を明記する。

## 軽微な指摘事項（改善提案）

### MIN-01: 既存シェル画面パスとの不整合
- **モジュール**: M-06, M-08
- **指摘内容**: 既存シェル画面のパスは`/vendors`（委託先）、`/incidents`（事故対応）だが、要件定義書でもこれらのパスを使用しており整合している。ただし、M-04の`/documents`は既存シェル`/documents`と一致するが、M-07の`/audit`やM-05の`/training`、M-09の`/application`も既存シェルと一致しており問題ない。確認事項として記載。
- **修正案**: 特に修正不要。整合性が取れている。

### MIN-02: Gemini 2.0 FlashとClaude APIの混在
- **モジュール**: AI連携全般
- **指摘内容**: MVP実装計画.mdでは「Google Gemini API (gemini-2.0-flash)」が技術スタックとして記載されている一方、フェーズ3では「Claude APIクライアント設定 (claude-sonnet-4-6)」とも記載されている。要件定義書ではGemini前提で記述されている。実際にどちらのLLMを使用するか、あるいは使い分けるかが不明確。
- **修正案**: AI基盤の使用LLMを統一するか、機能ごとの使い分け方針（例: Geminiを主LLM、Claudeをフォールバック等）を明記する。

### MIN-03: seed.tsへのデモデータ追加計画が未記載
- **モジュール**: 横断
- **指摘内容**: 各モジュールのデモデータ（サンプルリスク、教育計画、委託先等）がないと、実装後のデモ操作で空画面しか見えない。横断的考慮事項Cでseed追加に言及はあるが、各モジュールの具体的なデモデータ仕様がない。
- **修正案**: 各モジュールのセクションに「デモデータ」の項を追加し、seed投入する代表的レコード（2-3件）の概要を記載する。

### MIN-04: 既存のAiUsageLog.featureへの追加値が未定義
- **モジュール**: AI連携全般
- **指摘内容**: 既存の`AiUsageLog.feature`に `REGISTER_CANDIDATE | RISK_CANDIDATE | SUMMARIZE | CHAT | CHANGE_IMPACT | RESEARCH_PROFILE | INTERVIEW_HYPOTHESIS`が定義されている。新規AI機能（`AUDIT_CHECKLIST`, `TRAINING_MATERIAL`, `VENDOR_QUESTIONNAIRE`, `INCIDENT_ASSESSMENT`, `CHANGE_REPORT`等）の追加値が未列挙。
- **修正案**: 各モジュールのAI連携セクションに、対応する`AiUsageLog.feature`の値を明記する。

### MIN-05: PDF出力の技術的手段が未記載
- **モジュール**: M-03, M-07, M-08, M-09
- **指摘内容**: 複数のモジュールでPDF出力が要件に含まれているが、技術スタックにはExcelJS（Excel出力）のみが記載されている。PDF出力のライブラリ（puppeteer, @react-pdf/renderer, jspdf等）が未選定。
- **修正案**: PDF出力のライブラリ選定を横断的考慮事項に追加する。MVPではExcel出力に限定し、PDFは将来対応とする選択肢も検討する。

### MIN-06: ファイルアップロード時のウイルススキャン考慮がない
- **モジュール**: エビデンスアップロード
- **指摘内容**: エビデンスアップロードでは多様なファイルを受け付けるが、ウイルススキャンの考慮がない。ローカルMVPでは問題ないが、将来のクラウド展開時に必要。
- **修正案**: 将来対応として言及するのみでMVPでは不要。

### MIN-07: QuizQuestionがSessionに紐づく設計の再検討
- **モジュール**: M-05
- **指摘内容**: `QuizQuestion`が`TrainingSession`に紐づいているが、同一教育計画の複数セッションで同じテストを使い回す場合、質問を毎回登録する必要がある。`TrainingPlan`に紐づけるか、`QuizTemplate`を導入したほうが運用効率が良い。
- **修正案**: `QuizTemplate`モデルを導入し、`TrainingPlan.quizTemplateId`で参照する設計に変更する。セッションごとのテスト結果は`TrainingResult`で管理する現設計を維持。

## 横断的な問題

### データモデル

1. **双方向リレーション定義の欠落**: 全新規モデルで`@relation`が片方向のみ（または未定義）。Prismaスキーマとして成立しない箇所が多数。実装着手前に全リレーションを洗い出す必要がある。
2. **既存モデルへの影響範囲の明示不足**: `Organization`, `User`, `RegisterItem`, `BusinessProcess`など既存モデルへの変更（逆リレーション追加、フィールド追加）が要件定義書内で散在しており、一覧化されていない。スキーママイグレーション時に漏れが生じるリスクがある。
3. **インデックス設計の不在**: 全新規モデルでインデックス定義（`@@index`）が未記載。`organizationId`, `fiscalYear`, `status`などの頻出フィルタ条件にインデックスが必要。SQLiteでも主要カラムへのインデックスはクエリ性能に影響する。

### API設計

1. **一貫したエラーレスポンス仕様の未定義**: 既存実装では`{ error: "メッセージ" }`形式が使われているが、新規APIのエラーレスポンス仕様が未定義。バリデーションエラー時のフィールドレベルエラー返却仕様も不明。
2. **ページネーション未考慮**: 全一覧APIで取得件数が増えた場合のページネーション仕様が未定義。MVPでは問題ないが、実運用を見据えると`limit/offset`または`cursor`ベースのページネーション設計を横断仕様として定義すべき。
3. **organizationIdスコーピングの実装パターン未統一**: 既存APIでは`session.user.organizationId`でスコーピングしているが、新規API全体でこのパターンを踏襲する旨の横断仕様記載がない。

### AI連携

1. **Gemini 2.0 Flashのコンテキストウィンドウ制約**: 監査チェックリスト生成（AF-029）では台帳・リスク・教育・過去指摘を材料にするが、全データを入力すると1Mトークンの制約に近づく可能性がある。大規模組織での入力データ選択・要約戦略が必要。
2. **PIIマスキングの適用範囲**: 既存のPIIマスキング処理がリスク候補生成、委託先分析、事故報告分析でも適用されるか未確認。特に事故情報には高感度な個人情報が含まれる可能性が高い。
3. **AI生成結果の品質保証フロー**: 全モジュールでAI候補生成があるが、「人による確認・採否判定」のUIフローが明示的に定義されているのはM-03のみ。他モジュール（教育教材、監査チェックリスト等）でも同様の確認フローを統一仕様として定義すべき。

### 権限設計

1. **GLOBAL_ADMINロールの扱い**: 既存`User.role`にGLOBAL_ADMINが存在するが、全モジュールの権限表にGLOBAL_ADMINの行がない。システム管理者の権限範囲を明確にすべき。
2. **AUDITORロールの扱い**: MED-01で指摘済み。権限表への追加が必要。
3. **「自部門のみ」制約の実装パターン**: 複数モジュールでDEPT_STAFFに「自部門のみ」制約があるが、部門スコーピングの具体的実装パターン（session.user.departmentIdによるフィルタ）が横断仕様として未定義。
