以下の業務領域はMVPスコープ外とし、将来フェーズで対応する。

| 業務領域 | データモデル参照 | 除外理由 | 将来対応方針 |
|---------|----------------|---------|-------------|
| 本人対応・苦情相談管理 | Entity 35 ComplaintCase / DataSubjectRequestCase | 開示・訂正・利用停止等の本人請求は発生頻度が低く、MVP段階では手動運用で対応可能。記録はM-04文書管理でファイル保管可能。 | フェーズ2でケース管理モジュールとして実装。受付→対応→完了のワークフロー、期限管理、台帳連携を含む。 |
| 変更管理 | Entity 33 ChangeRequest, WF-03 | 変更申請フローは組織の承認文化に依存し、MVP段階ではM-04文書管理の文書改定機能＋台帳の版管理で最低限の変更記録を維持可能。 | フェーズ2でWF-03を実装。変更起票→影響分析→台帳・リスク連動→承認のフローを定義。 |
| 第三者提供管理 | Entity 27 ThirdPartyProvisionCase | 委託と第三者提供は法的に区別が必要だが、MVPでは台帳明細のthirdPartyProvisionフィールド（NONE/DOMESTIC/OVERSEAS）とM-06委託先管理で基本的な管理は可能。 | フェーズ2でM-06の拡張として第三者提供案件管理を追加。提供先・根拠・同意・停止請求管理を含む。 |

### 横断API仕様

1. **organizationIdスコーピング**: 全APIは`session.user.organizationId`でデータをスコーピングする。クエリ条件に必ず`organizationId`を含め、他組織のデータへのアクセスを防止する。
2. **PUTは部分更新を許容**: PUTリクエストは送信されたフィールドのみ更新する（未送信フィールドは変更しない）。ステータス遷移は専用エンドポイント（`/approve`, `/close`等）を使用する。
3. **エラーレスポンス**: `{ error: string, details?: Record<string, string> }` 形式。`details`はフィールドレベルのバリデーションエラーに使用。
4. **fiscalYear統一仕様**: 全モデルで`fiscalYear Int`（西暦4桁の整数、例: 2025）に統一する。

## 1. M-03: リスク管理モジュール

### 1.1 目的

台帳で特定した個人情報について、取得から消去までのライフサイクル各局面でリスクを洗い出し、評価・対策・残留リスクを一元管理する。JIS Q 15001の J.3.1.3（リスクアセスメント及びリスク対応）に直接対応する。

### 1.2 ユーザーストーリー

1. **個人情報管理者（PRIVACY_OFFICER）** として、承認済み台帳明細に対してリスク候補をAIで一括生成し、部門担当者に評価依頼を出したい。
2. **部門担当者（DEPT_STAFF）** として、自部門の業務プロセスに紐づくリスク一覧を確認し、発生可能性・影響度を評価して管理策を入力したい。
3. **個人情報管理者（PRIVACY_OFFICER）** として、全社のリスクマップ（ヒートマップ）を閲覧し、高リスク項目を優先的に対策したい。
4. **トップマネジメント（TOP_MANAGEMENT）** として、残留リスクの受容判断を承認し、証跡として記録を残したい。
5. **個人情報管理者（PRIVACY_OFFICER）** として、前年度のリスク評価と比較して差分レポートを生成し、更新申請に添付したい。

### 1.3 画面設計

| 画面 | パス | 構成要素 |
|------|------|----------|
| リスク一覧 | `/risk` | フィルタ（業務・深刻度・ステータス）、リスクテーブル、ヒートマップ切替、AI一括生成ボタン |
| リスク詳細 | `/risk/[id]` | リスク情報、管理策リスト、残留リスク、関連台帳リンク、エビデンス、承認ステータス、コメント |
| リスク新規作成 | `/risk/new` | 対象台帳選択、ライフサイクル局面選択、リスク内容入力、AI候補採用 |
| リスク評価入力 | `/risk/[id]/evaluate` | 発生可能性（5段階）、影響度（5段階）、管理策入力、担当者・期限設定 |
| リスクマップ | `/risk/heatmap` | 発生可能性 x 影響度のヒートマップ、ドリルダウン |
| リスクレポート | `/risk/report` | 年度別比較、Excel/PDF出力、申請向けパッケージ |

```prisma
model RiskAssessment {
  id                String   @id @default(cuid())

  targetScope       String   @default("ALL") // ALL | PROCESS | ITEM — 評価対象スコープ

  @@index([organizationId])

  @@index([status])

  lifecyclePhase      String           // ACQUISITION | INPUT | TRANSFER | TRANSMISSION | USE | PROCESSING | STORAGE | BACKUP | DELETION | DISPOSAL
  threatCategory      String           // LEAKAGE | LOSS | DAMAGE | FALSIFICATION | UNAUTHORIZED_ACCESS | EXCESS_RETENTION | MISDIRECTION | OTHER
  riskDescription     String
  riskOwner           String?

  impact              Int?             // 影響度 1-5

  @@index([registerItemId])
  @@index([businessProcessId])
  @@index([status])

  evidenceNote    String?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  riskItem        RiskItem @relation(fields: [riskItemId], references: [id])
  responsible     User?    @relation(name: "ControlMeasureResponsible", fields: [responsibleId], references: [id])

}

model ResidualRisk {
  id              String   @id @default(cuid())
  riskItemId      String   @unique
  likelihood      Int
  impact          Int
  residualLevel   String           // LOW | MEDIUM | HIGH
  accepted        Boolean  @default(false)
  acceptedById    String?
  acceptedAt      DateTime?
  justification   String?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  riskItem        RiskItem @relation(fields: [riskItemId], references: [id])
  acceptedBy      User?    @relation(name: "ResidualRiskAcceptor", fields: [acceptedById], references: [id])
}
```

### 1.6 AI連携

- **リスク候補生成（AF-026）**: 承認済み台帳明細をGeminiに渡し、ライフサイクル各局面のリスク候補を生成。PIIマスキング適用。`AiUsageLog.feature = "RISK_CANDIDATE"`
- **管理策候補生成（AF-027）**: 識別済みリスクに対して安全管理措置候補を提案。`AiUsageLog.feature = "RISK_MEASURE_CANDIDATE"`
- **情報不足検出（AF-032）**: 評価が不十分なリスク項目を自動指摘。
- **前年度差分要約（AF-028）**: 前年度評価との変更点を自然言語で説明。`AiUsageLog.feature = "RISK_DIFF_SUMMARY"`

## 2. M-04: 文書管理（ドキュメント管理）モジュール

### 2.1 目的

PMS運用に必要な方針、内部規程、様式、手順書、計画書、記録類を版管理し、必要時に容易に参照でき、保護された状態で保持する。JIS Q 15001の J.4.3.2（文書化した情報の管理）および J.4.3.3（記録の管理）に対応する。

### 2.2 ユーザーストーリー

1. **個人情報管理者（PRIVACY_OFFICER）** として、PMS文書を登録し、版管理したい。改定時には旧版も参照可能にしたい。
2. **個人情報管理者（PRIVACY_OFFICER）** として、文書改定時に改定理由・内容・施行日を記録し、承認を経て施行したい。
3. **部門担当者（DEPT_STAFF）** として、自部門で必要な文書や様式を検索・閲覧・ダウンロードしたい。
4. **個人情報管理者（PRIVACY_OFFICER）** として、文書一覧表をExcelで出力し、申請時に提出したい。
5. **トップマネジメント（TOP_MANAGEMENT）** として、文書改定の承認を行い、承認証跡を残したい。

### 2.3 画面設計

| 画面 | パス | 構成要素 |
|------|------|----------|
| 文書一覧 | `/documents` | カテゴリ別フォルダビュー、検索バー、フィルタ、文書テーブル |
| 文書詳細 | `/documents/[id]` | 現行版表示、版履歴、関連エビデンス、ダウンロード、承認ステータス |
| 文書登録/改定 | `/documents/new` or `/documents/[id]/revise` | カテゴリ選択、タイトル、ファイルアップロード、改定理由、施行日、承認者指定 |
| 版比較 | `/documents/[id]/compare` | 左右並列表示（旧版 vs 新版）、変更箇所ハイライト |
| PMS文書一覧表 | `/documents/index` | 文書体系ツリー、Excel出力ボタン |

### 2.8 既存機能との連携

- **M-05 教育管理**: 教育資料を文書として版管理。
- **M-07 監査・是正管理**: 監査チェックリスト、監査報告書の版管理。
- **M-09 申請・更新管理**: PMS文書一覧表を申請パッケージに含める。
- **ダッシュボード**: 文書数サマリー、改定待ち件数を表示。

## 3. M-05: 教育管理モジュール

### 3.1 目的

個人情報保護に関する教育の計画・実施・理解度確認・記録保管を一元管理する。JIS Q 15001の J.4.2.2（力量、教育及び認識）に対応し、少なくとも年1回の教育実施と理解度確認が求められる。

### 3.2 ユーザーストーリー

1. **個人情報管理者（PRIVACY_OFFICER）** として、年間教育計画を作成し、対象者・実施予定日・教育内容を登録したい。
2. **個人情報管理者（PRIVACY_OFFICER）** として、教育セッションを実施し、出席・理解度テスト結果を記録したい。
3. **部門担当者（DEPT_STAFF）** として、自分に割り当てられた教育を受講し、理解度テストに回答したい。
4. **個人情報管理者（PRIVACY_OFFICER）** として、AIに教育教材の下書きを生成させたい。
5. **トップマネジメント（TOP_MANAGEMENT）** として、全社の教育実施状況サマリーを確認したい。
6. **個人情報管理者（PRIVACY_OFFICER）** として、教育実施サマリーをExcel/PDFで出力し、申請書類に添付したい。

### 3.3 画面設計

| 画面 | パス | 構成要素 |
|------|------|----------|
| 教育管理トップ | `/training` | 年間カレンダー、教育計画一覧、実施状況サマリーカード |
| 教育計画作成 | `/training/plans/new` | 教育名、対象範囲、予定日、教育形式、教材選択、理解度テスト設定 |
| 教育計画詳細 | `/training/plans/[id]` | 計画情報、対象者リスト、受講進捗、テスト結果一覧 |
| セッション実施 | `/training/sessions/[id]` | 出席入力、テスト配布・回収、受講証明生成 |
| 受講者用画面 | `/training/my` | 自分の未受講一覧、テスト回答、受講履歴 |
| 理解度テスト | `/training/sessions/[id]/quiz` | 設問表示、回答入力、自動採点 |
| 教育サマリー | `/training/report` | 年度別実施率、合格率、未受講者リスト、Excel/PDF出力 |

### 3.4 データモデル

```prisma
model TrainingPlan {
```

## 4. M-06: 委託先管理モジュール

### 4.1 目的

個人情報の取扱いを委託している外部事業者を特定し、選定基準・契約条項・監督状況を一元管理する。JIS Q 15001の J.4.5.5.4（委託先の監督）に対応する。

### 4.2 ユーザーストーリー

1. **個人情報管理者（PRIVACY_OFFICER）** として、全ベンダーを登録し、委託範囲・契約状況・再委託有無を管理したい。
2. **個人情報管理者（PRIVACY_OFFICER）** として、委託先に安全管理措置の質問票を送付し、回答を回収・評価したい。
3. **部門担当者（DEPT_STAFF）** として、自部門が利用しているSaaS/外部サービスを委託先として申請したい。
4. **個人情報管理者（PRIVACY_OFFICER）** として、契約更新期限や再評価期限のリマインドを受け取りたい。
5. **トップマネジメント（TOP_MANAGEMENT）** として、委託先全体の評価状況サマリーを閲覧したい。

## 5. M-07: 監査・是正管理モジュール

### 5.1 目的

内部監査の計画・実施・指摘・報告書作成から、是正処置の起票・原因分析・対策・有効性確認までを一貫管理する。JIS Q 15001の J.4.6.2（内部監査）および J.4.5.7.2（不適合及び是正処置）に対応する。

**注**: マネジメントレビュー（J.4.6.3）は独立モジュールM-11として定義（セクション8参照）。

### 5.2 ユーザーストーリー

1. **監査責任者（AUDITOR）** / **個人情報管理者（PRIVACY_OFFICER）** として、年間内部監査計画を作成し、対象部門・範囲・基準・監査員を設定したい。
2. **監査責任者（AUDITOR）** として、AIに監査チェックリスト（質問案）を生成させたい。
3. **監査責任者（AUDITOR）** として、監査実施結果を登録し、監査報告書を生成したい。
4. **部門担当者（DEPT_STAFF）** として、自部門への監査指摘に対する是正処置を起票したい。
5. **トップマネジメント（TOP_MANAGEMENT）** として、監査結果サマリーと是正状況を確認したい。
6. **個人情報管理者（PRIVACY_OFFICER）** として、監査実施サマリーをExcel/PDFで出力したい。

## 6. M-08: 事故対応モジュール

### 6.1 目的

5. **トップマネジメント（TOP_MANAGEMENT）** として、事故発生状況を速やかに把握したい。

## 8. M-11: マネジメントレビューモジュール（CRI-01対応・新規追加）

### 8.1 目的

トップマネジメントが少なくとも年1回、PMSの運用状況を総合的にレビューし、改善の機会・変更の必要性を判断する。JIS Q 15001の J.4.6.3（マネジメントレビュー）に直接対応する。

**インプット**（J.4.6.3で求められるレビュー材料）:
- 監視・測定結果（各モジュールの運用状況サマリー）
- 内部監査結果（M-07）
- 不適合及び是正処置の状況（M-07）
- 前回レビューからのフォローアップ
- PMSに影響を与える外部・内部の課題の変化
- 利害関係者からのフィードバック
- リスク対応計画の状況（M-03）
- 改善の機会

**アウトプット**:
- PMSの変更の必要性に関する決定
- 改善指示・方針変更
- 資源の割当
- 次年度の方針・目標

### 8.2 ユーザーストーリー

1. **個人情報管理者（PRIVACY_OFFICER）** として、マネジメントレビューの入力資料を各モジュールから自動収集し、レビュー資料ドラフトを作成したい。
2. **個人情報管理者（PRIVACY_OFFICER）** として、レビュー会議のアジェンダを設定し、各議題に対する資料を紐付けたい。

4. **個人情報管理者（PRIVACY_OFFICER）** として、レビュー結果（議事録・決定事項・改善指示）を記録し、フォローアップ管理したい。
5. **個人情報管理者（PRIVACY_OFFICER）** として、マネジメントレビューサマリーをExcel/PDFで出力し、申請書類（M-09）に含めたい。

- **前回レビュー比較**: 前回レビューの決定事項と今回の状況を比較し、進捗サマリーを生成。`AiUsageLog.feature = "REVIEW_COMPARISON"`

### 8.7 ワークフロー

```
ManagementReview:
  DRAFT → PREPARED → IN_REVIEW → APPROVED → LOCKED
                   ↘ DRAFT（差戻し）

  DRAFT: 入力資料収集・アジェンダ設定中
  PREPARED: レビュー資料準備完了、レビュー実施待ち
  IN_REVIEW: レビュー会議実施中（議事録・決定事項入力）
  APPROVED: トップマネジメント承認済み
  LOCKED: 版固定（申請パッケージ向け）

ManagementReviewDecision（フォローアップ）:
  OPEN → IN_PROGRESS → COMPLETED
                     → CARRIED_FORWARD（次回レビューに持越し）
```
